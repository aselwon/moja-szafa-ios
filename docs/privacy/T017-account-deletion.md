# T017 — Account deletion implementation and deployment gates

## Implemented

Account settings (also accessible before onboarding is completed) provide PL/EN deletion disclosure, subscription management, reauthorization challenge, and destructive confirmation. Subscription cancellation is never checked. A verified email code is the proposed reauthorization mechanism for email and Apple identities, including private relay. The app never accepts an email address as the account identity.

The client persists a non-secret operation UUID and submitted/accepted flags per account. After submission, normal API access and wardrobe presentation are fenced until deletion recovery or logout. Exact retries retain the operation UUID. On relaunch, a submitted request goes to recovery without refreshing a revoked session. Acknowledgement means queued, not erased. Accepted requests clear local profile data, the injected offline store/outbox, and Keychain credentials. Local cleanup failures are retried on launch; they do not undo remote deletion. No widget implementation/cache exists yet; integrating one must extend this cleanup hook. Photo import drafts currently live in view memory and disappear when the authenticated view is removed.

Migration 009 adds one durable job per owner, an atomic profile tombstone and image publication fence, restrictive owner-read policies, five-minute leases, fencing tokens, bounded retries (10 claims), and a dead-letter state. A successful finish purges profile-owned tables (including mutation replay payloads) and account-specific operator audit. A minimal job receipt and retired image IDs remain for replay/restore suppression. A late worker cannot finalize with an expired or replaced lease.

The deletion worker orders external actions: invalidate all sessions → revoke Apple tokens → erase private images → delete auth identity → purge domain data. Failures retain the job and block later steps. All adapters must be idempotent; a lost commit is recovered through the lease. Existing image sweeping continues to remove late writes to retired image IDs.

## Gateway contract (not deployed)

The repository's T013 auth gateway is not implemented or configured. T017 supplies the Swift client, trusted request handler (`backend/deletion/service.mjs`), PostgreSQL store and worker, **not a working production auth/Apple integration**. `AppDependencies.live()` remains unconfigured. Do not enable deletion or claim end-to-end acceptance until the following real adapters exist and are verified.

- `POST /auth/v1/deletion/challenge`, bearer plus `{operationID: UUID}` → `{challengeID: UUID}`. Send a short-lived deletion-purpose code only to the authenticated owner's verified address; enforce expiry, resend limits, attempt limits and enumeration protection. Bind the challenge to owner and operation. Never use a caller-supplied address or silently link identities.
- `POST /auth/v1/deletion`, bearer plus `{operationID: UUID, challengeID: UUID, code: string}` → HTTP 202 `{jobID: UUID, status: "queued"}` (or a replayed succeeded receipt). Call `requestDeletion` with a real `verifyDeletionProof` adapter. Only that adapter derives the owner; service-role SQL is not a public RPC. Return errors as `{error:{code,message,request_id}}` without provider details.
- Proof consumption and replay authorization must be durable. Exact proof replay must recover the same job after a timeout, including after sessions are revoked. For recovery ONLY, an old cryptographically verified bearer may identify the owner, but must not authorize any action without a fresh valid deletion challenge or a previously consumed exact proof. Never grant ordinary resource or refresh access with it. Preserve only the protected recovery metadata necessary for the approved recovery interval, even after auth-identity deletion. This special recovery route requires security review and integration tests before activation.
- `revokeSessions(owner, jobID)` invalidates every refresh session, and resource gateways deny the tombstone immediately even for unexpired access JWTs. Direct database reads are fenced by RLS.
- `revokeAppleTokens(owner, jobID)` enumerates linked identities by subject, not email; obtains revocable Apple credentials from encrypted server storage and verifies revocation. T013 currently sends only identity tokens: authorization-code exchange and durable encrypted revocable-token capture remain an integration dependency. Absence of a token for a linked Apple identity is a retry/escalation, never success. For an account proven to have no Apple identity it is a legitimate no-op. Do not delete the credential before a recoverable revocation result is recorded.
- `removeImages(owner, jobID)` removes all originals, thumbnails, temporary/retired uploads, and any exports from the actual private storage. Use the upload ledger rather than just current garment relations; verify absence before returning. Keep the existing retired-image sweeper running for delayed uploads.
- `deleteAuthIdentity(owner, jobID)` deletes the real auth principal, treats already absent as success, and retains no raw tokens in logs. It must not run before Apple revocation.

Run the worker under the deployment supervisor using `node backend/deletion/worker.mjs /operator-controlled/adapter.mjs`; libpq supplies the dedicated database credentials outside argv. The adapter exports the four functions above. Each operation has a 45-second caller deadline; the adapter must itself cancel/terminate timed-out network/storage operations. Missing adapters fail startup. No adapter or paid API was invoked here.

## Backup retention and restore: unresolved release gate

There is no approved backup retention policy or configured provider retention evidence in this repository. No retention duration, legal exception, or completed backup erasure is asserted. The owner must approve and publish a policy matching database PITR/snapshots, object versions, auth backups, operator logs and deletion-ledger retention. Configure automatic expiry and record evidence. Production activation is blocked until this is done.

Maintain a protected deletion suppression ledger outside the backup being restored. Before reopening a restored environment to traffic or workers, replay every subsequent deletion, invalidate restored sessions, reapply tombstones, revoke restored credentials as necessary, purge restored objects and domain rows, and verify absence. Test a backup predating a deletion. Never restore the deletion ledger solely from that older backup. Retain pseudonymous fences only for the approved backup/replay horizon; define and test their eventual expiry. No restore drill has been performed.
