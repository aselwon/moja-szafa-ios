# T023 — availability and archiving

Availability (`available`, `laundry`, `unavailable`) is independent of archiving.
The detail controls persist a local edit before attempting synchronization. Archive
and restore preserve price, historical wear dates, images and initial estimates;
CPW inputs are unchanged. The archive filter provides the return path to archived
items. Version conflicts offer an explicit server/local choice. A queued or
ambiguous write retains its operation UUID across restarts.

Migration 012 adds an optional `archived` boolean to the existing save contract
and includes it in synchronization fields. Omission preserves server archive state
for older clients and already queued operations. Existing migrations are unchanged.
The configured authentication composition uses the account-specific OfflineStore;
production endpoints remain explicitly unconfigured as before.

The AI executor requires explicit availability/archive fields from its trusted
runtime resolver, excludes ineligible candidates before dispatch, and resolves
again to reject newly ineligible returned IDs. The deployment runtime must still
validate ownership and revalidate atomically when saving an outfit. Full outfit
creation and its transaction are outside T023 and are not claimed as implemented.

## Device acceptance checks

Using a configured staging build and the same account on two iPhones, record a
wear and known price, change each availability state, then archive. Refresh the
second phone or foreground the wardrobe; confirm both states match. Check the
archive filter and restore while keeping laundry status. Confirm historical days
and CPW inputs are identical. Repeat offline, terminate/reopen, reconnect and
refresh. Make competing edits and exercise both conflict choices. Check PL/EN,
VoiceOver and large Dynamic Type. Capture evidence from the actual build.

Real-device synchronization and the production AI/runtime integration need these
external checks; local fixtures are not evidence of a deployed service.
